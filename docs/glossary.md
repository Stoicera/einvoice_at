# Glossary / Glossar

German domain terms stay German in code, docs and messages where they are legally precise. English explanation for each.

| Begriff (DE) | English explanation |
|---|---|
| **ebInterface** | Austrian national XML e-invoice standard, maintained by AUSTRIAPRO. Version 6.1 is current; 7.0 announced for Q4 2026. |
| **Auftragsreferenz** | Order reference. Mandatory for invoices to the Austrian federal government (B2G via e-rechnung.gv.at). |
| **Lieferantennummer** | Supplier number assigned by the contracting authority; required in federal B2G invoices. Canonical `Invoice.supplierNumber`, mapped to `Biller/InvoiceRecipientsBillerID` in ebInterface 6.1 (module `mapping`), enforced on the validation side by `AT-B2G-04` (`validation/src/main/resources/schematron/at-b2g-ebinterface-6.1.sch`, M3). |
| **USt** | Umsatzsteuer — Austrian VAT. Standard rates: 20 %, reduced 13 % / 10 %, plus 0 % and reverse charge. |
| **UID(-Nummer)** | Umsatzsteuer-Identifikationsnummer — VAT identification number (ATU…). |
| **e-rechnung.gv.at** | The Austrian federal portal/web service that receives B2G e-invoices (ebInterface or Peppol BIS). |
| **Prüfbericht** | Validation report. The structured, German-first output of the validation pipeline. |
| **kaufmännisches Runden** | Commercial rounding: round half away from zero (`HALF_UP`). The rounding mode used throughout `Money`. |
| **Kennzahl (KZ)** | Figure/total field referenced in Austrian tax contexts, abbreviated KZ (see SPEC §7: KZ totals); used in total-consistency business rules. |
| **Kleinunternehmer** | Small-business owner exempt from USt per § 6 Abs 1 Z 27 UStG. Modelled as VAT category E (exempt) without a UID. |
| **Schematron** | XML rule-validation language: business rules expressed as XPath `assert`/`report` statements, layered on top of a schema for checks XSD alone cannot express (e.g. "if category X then field Y is required"). ebInterface ships no official Schematron, so the `validation` module's `AT-B2G-01`/`03`/`04`/`05` rules run a project-own `.sch` file (see ADR-0004); Peppol BIS 3.0's official Schematron rule sets (via phive-rules) arrive with M4. |
| **SVRL** | Schematron Validation Report Language — the XML output a Schematron engine produces, one `successful-report`/`failed-assert` element per rule per node checked. `SchematronStage` maps each `failed-assert` to a bilingual `Finding` via `SchematronRuleCatalog`. |
| **Storno** | Cancellation/reversal of an invoice. Some senders express a Storno as a standard type-380 commercial invoice with a negative payable amount instead of a proper type-381 credit note; the canonical model's non-negative `payableAmount` invariant rejects that shape as constructed, so import mapping (M4) must normalize a negative-total 380 to a 381 before it reaches `core` (ADR-0003). |
| **Prüfsumme** | Checksum. Used here for the IBAN mod-97 checksum (`AT-B2G-02`, module `validation`): the check digits sit at positions 3–4, immediately after the two-letter country code, and a valid IBAN yields mod-97 remainder of 1 when the first four characters are moved to the end before computation. This catches a transposed or mistyped digit that a plain length/shape check (the XSD) would miss. |
| **Bundesdienststellen** | Austrian federal government service units / agencies. The AT-B2G Schematron rules `AT-B2G-01`/`03`/`04`/`05` (`validation/src/main/resources/schematron/at-b2g-ebinterface-6.1.sch`, `SchematronRuleCatalog.java`) require an Auftragsreferenz, a Biller e-mail address, a Lieferantennummer and a `PaymentMethod` respectively for invoices addressed to Bundesdienststellen, per e-rechnung.gv.at's federal B2G obligation. |
| **Empfängerkonto** | Beneficiary/recipient bank account. The IBAN mod-97 checksum rule (`AT-B2G-02`, `BusinessRuleStage.java`) validates every IBAN present under `PaymentMethod/UniversalBankTransaction/BeneficiaryAccount` (Empfängerkonto) without ever echoing the IBAN itself in the finding — only its 1-based position among the document's beneficiary accounts. |
| **Übergang der Steuerschuld** | Transfer of VAT liability to the invoice recipient — the legal effect of reverse charge (§ 19 UStG). § 11 Abs 1a UStG requires the invoice to carry a Hinweis auf den Übergang der Steuerschuld; `InvoiceToEbInterface61Mapper.exemptionComment` leads a category-AE tax item's comment with this exact wording, distinct from the `"Steuerbefreiung: "` lead-in used for a genuine tax exemption (category E) — reverse charge is a liability shift, not an exemption, and labeling it one is the kind of wording an Austrian auditor flags (M2 hostile-review finding A4; see the mapper's own Javadoc mapping table for the two wordings side by side). |
| **Rechnungssteller** | Invoice issuer (the ebInterface `Biller`). e-rechnung.gv.at's federal B2G profile requires a Rechnungssteller contact e-mail address (`Biller/Address/Email`); the AT-B2G Schematron rule `AT-B2G-03` (`validation/src/main/resources/schematron/at-b2g-ebinterface-6.1.sch`, M3) enforces its presence. |
| **Zahlungsmethode** | Payment method (the ebInterface `PaymentMethod` element). The AT-B2G Schematron rule `AT-B2G-05` (M3) requires one to be present — either `UniversalBankTransaction` or `NoPayment`, the only two variants `InvoiceToEbInterface61Mapper` ever emits. |
| **Mandant** | Tenant — the isolation boundary of the multi-tenant `app` module. A Keycloak login (identified by its stable `sub` claim) or an API key maps to exactly one `TenantEntity` (`tenant.external_subject`, unique), auto-provisioned on the first authenticated request (`TenantProvisioningService`, M3). Every invoice, report, API key and audit event carries a `tenant_id`, and tenant-scoped repository finders keep one Mandant from ever seeing another's rows (see ADR-0005 and ADR-0006). |
| **API-Schlüssel** | API key — a machine credential for headless access to the REST API, presented as the `X-Api-Key` request header. Format `eiv_` + URL-safe random; only its SHA-256 is stored (`api_key.key_hash`), the plaintext being shown exactly once at creation and never retrievable again. Minted and revoked only by an OAuth2 (JWT) login, never by another API key (`ApiKeyController` / `ApiKeyService`; ADR-0006, M3). Revocation is soft — `revoked_at` is stamped and the row retained, so the audit trail survives. |
| **Lieferdatum** | Delivery date (EN 16931 BT-72) — the single day a supply was rendered. Modelled on `core` as `Invoice.deliveryDate` (added M3), mutually exclusive with the Leistungszeitraum: § 11 Abs 1 Z 4 UStG requires the day of delivery *or* the period, never both, and that invariant is enforced by `Invoice`. Maps to the ebInterface `Delivery/Date` branch (module `mapping`). |
| **Leistungszeitraum** | Service period (EN 16931 BG-14; start BT-73, end BT-74) — the span of days over which a supply was rendered, used when it is not a single-day event. Modelled on `core` as `Invoice.servicePeriod`, a `ServicePeriod(from, to)` record (added M3) that rejects a `to` before its `from`; mutually exclusive with the Lieferdatum (see there). Maps to the ebInterface `Delivery/Period` branch (module `mapping`). |

## M4 — UBL, Peppol und Konvertierung

| Begriff | Erklärung |
|---|---|
| **UBL** (Universal Business Language) | OASIS-XML-Standard für Geschäftsdokumente. Peppol BIS Billing 3.0 ist eine *Customisation von* UBL 2.1, keine eigene Syntax: alles, was BIS zusätzlich fordert, ist Schematron. |
| **Peppol BIS Billing 3.0** | Der europäische Rechnungs-Regelsatz von OpenPeppol auf Basis von EN 16931. Wird hier **unverändert ausgeführt**, an einer im Code gepinnten Version (ADR-0007). |
| **VES** (Validation Executor Set) | phives Bündel aus XSD- und Schematron-Stufen für genau ein Dokument-Profil in genau einer Version. Ein Peppol-VES enthält XSD, EN-16931- und BIS-Regeln bereits in der richtigen Reihenfolge. |
| **EAS** (Electronic Address Scheme) | Vierstellige Codeliste, die sagt, *in welchem Namensraum* eine elektronische Adresse zu lesen ist (BT-34-1/BT-49-1). Ohne Schema ist eine Endpoint-ID bedeutungslos. |
| **Elektronische Adresse** (BT-34/BT-49) | Das *Postfach im Netzwerk*, an das ein Dokument zugestellt wird — nicht die Kontakt-E-Mail (BT-43/BT-58). Peppol verlangt sie, ebInterface 6.1 hat kein Element dafür. Wird nie aus der UID synthetisiert (ADR-0007 Entscheidung 5). |
| **Verlust-Report** (`ConversionReport`) | Was eine Konvertierung nicht mitnehmen konnte, pro Dokument und deutsch zuerst: `CONV-01` Verlust, `CONV-02` übersetzte Konvention, `CONV-03` verschobenes Feld, `CONV-04` abweichende Summe. |
| **Gutschrift als eigene Syntax** | UBL macht die Dokumentart zum *Wurzelelement*: BT-3 380 ist ein `ubl:Invoice`, 381 ein `ubl:CreditNote` — anderer Namensraum, anderer JAXB-Typ, anderer Peppol-Regelsatz. ebInterface unterscheidet dieselbe Sache über ein Attribut. |
| **Druckansicht** | Die menschenlesbare PDF-Fassung einer Rechnung. *Kein* Hybrid-Dokument (ZUGFeRD/Factur-X): es ist kein XML eingebettet (ADR-0008 Entscheidung 5). |

## M5 — Web-UI und KI-Erklärungen

| Begriff | Erklärung |
|---|---|
| **Prüfer-Seite** | Die öffentliche Validierungsseite (`/validator`) — der Lead-Magnet aus PRD §2. Anonym, rate-limited, und der Upload wird **nicht gespeichert**: sie läuft durch dieselbe `ReportService.validate(bytes, Optional.empty())` wie der anonyme REST-Endpunkt, damit die Zusage genau eine Implementierung hat. |
| **Prüfbericht** | Die Darstellung eines `ValidationReport` für Menschen: Befunde nach Schweregrad gruppiert (Fehler, Warnung, Hinweis), je Befund Regel-ID, Fundstelle und deutscher Klartext — Englisch als zweite, leise Zeile für Entwickler. |
| **DSGVO-Hinweis** | Die Zusage über der Upload-Fläche, dass die Datei nur im Arbeitsspeicher geprüft und danach verworfen wird. MILESTONES nennt ihn ausdrücklich; ein Test hält ihn auf der Seite und ein zweiter prüft, dass er stimmt (die Zeilenzahl in `report` bewegt sich nicht). |
| **Filterkette** (`SecurityFilterChain`) | Seit M5 gibt es **zwei**: `/api/**` bleibt zustandslos mit abgeschaltetem CSRF-Schutz, die Browser-Oberfläche bekommt Session, aktiven CSRF-Schutz und `oauth2Login`. Die Reihenfolge ist tragend — ein API-Pfad außerhalb von `/api/**` würde in der Browser-Kette landen und einen Login-Redirect statt eines `401` liefern (ADR-0009). |
| **`LlmClient`** | Der schmale Provider-Port, den ENGINEERING_STANDARDS §8 verlangt: eine Methode, kein Streaming, keine Werkzeuge, kein Gesprächszustand. Alles oberhalb des Ports weiß nicht, welcher Anbieter läuft; ein zweiter Anbieter ist ein Schwesterpaket. |
| **PII-Scrubbing** | Das Maskieren personenbezogener Daten, **bevor** eine Anfrage die Plattform verlässt: IBAN → `[IBAN]`, E-Mail → `[E-MAIL]`, UID → `[UID]`, Ziffernfolgen ab 7 Stellen → `[NUMMER]`, vom Aufrufer benannte Namen → `[NAME]`. Regel-IDs werden bewusst **nicht** maskiert — ein maskierter Regelbezeichner machte den Befund unerklärbar. |
| **Degradierbarkeit** | Die Zusage, dass das KI-Feature ausfallen *oder* abgeschaltet sein kann, ohne dass die Plattform etwas verliert. Technisch: `FindingExplainer.explain` wirft **nie**, und bei ausgeschaltetem Flag existiert gar kein Provider-Client — es gibt also keine Schaltfläche, die scheitern könnte (M5-Abnahme „KI abschaltbar ohne Funktionsverlust"). |
| **Feature-Flag** (`features.ai-explanations`) | Der Schalter aus SPEC §2. Standard **aus**: das Feature kostet Geld pro Klick und schickt Text an einen Dritten, also schaltet ein Betreiber es wissentlich ein. Ist es an und fehlt der Schlüssel, startet die Anwendung nicht — statt einen Client zu betreiben, der nicht funktionieren kann. |
| **Assistent** (Wizard) | Die vierstufige Rechnungserstellung im Dashboard — Kopfdaten, Parteien, Positionen, Zahlung & Prüfen. Server-gerendert, jeder Schritt ein POST mit Redirect, kein JavaScript (ADR-0009 Entscheidung 5). Der letzte Schritt ruft **dieselbe** `InvoiceService.create` wie `POST /api/v1/invoices`, damit es nicht zwei Definitionen von „Rechnung anlegen" gibt. |
| **Entwurf** (`InvoiceDraft`) | Der halbfertige Zustand des Assistenten, in der HTTP-Session. Session statt versteckter Formularfelder, weil Schritt 3 eine *Liste* sammelt; pro Session, also sieht ein zweiter Browser einen fremden Entwurf nicht. Validiert selbst nichts über „ist das Feld gefüllt" hinaus — die echten Regeln stehen in `core`, und zwei Definitionen von „gültige Rechnung" wären genau der Fehler, den das kanonische Modell verhindern soll. |
| **Danger Zone** | Der Bereich auf der Konto-Seite, der Mandant und alle Daten löscht (Art. 17 DSGVO). Bestätigung durch Eintippen des Wortes `LÖSCHEN` — ein Dialog bräuchte JavaScript und wäre mit einem versehentlichen Enter wegzuklicken, ein getipptes Wort entsteht nicht aus einem Fehlklick. |
| **Aufbewahrungsfrist** (retention) | Die Zeit, nach der ein Datensatz von selbst verfällt (Art. 5 Abs. 1 lit. e DSGVO). Hier: Prüfberichte 365 Tage, Protokoll-Einträge 730 Tage, `0` = unbegrenzt. **Rechnungen haben keine** — § 132 BAO verpflichtet zu sieben Jahren, und automatisches Löschen wäre Schaden, nicht Datenschutz (ADR-0011). |
| **§ 132 BAO** | Bundesabgabenordnung: Bücher, Aufzeichnungen und Belege — also auch Rechnungen — sind **sieben Jahre** aufzubewahren. Der Grund, warum der Aufbewahrungs-Job Rechnungen niemals anfasst und ein Test eine zehn Jahre alte Rechnung durch einen Purge schickt. |
| **Löschung auf Verlangen vs. Ablauf** | Zwei verschiedene Vorgänge mit verschiedenen Regeln, absichtlich getrennte Klassen: `TenantErasureService` (Art. 17, löscht *alles*, auch Rechnungen, weil gefragt wurde) und `RetentionService` (Art. 5, löscht *nur* Berichte und Protokolle). Ein gemeinsamer Codepfad hätte den Unterschied zu einem `if` gemacht. |
| **Flash-Attribut** | Der Mechanismus, mit dem ein neu erzeugter API-Schlüssel **genau einmal** angezeigt wird: er überlebt exakt eine Weiterleitung (POST-Redirect-GET), also kann ein Reload das Geheimnis nicht erneut zeigen. Gespeichert wird nur sein Hash. |
| **OIDC-Discovery** | Das automatische Abholen von `/.well-known/openid-configuration`. In Docker ein Fallstrick: Spring Boot löst einen Provider-`issuer-uri` **beim Start** auf, und die browserseitige URL ist im Container der eigene Loopback — die Anwendung startet dann überhaupt nicht. Deshalb werden die vier Endpunkte explizit gesetzt (ADR-0009 Entscheidung 6). |

## M6 — Betrieb und Observability

| Begriff | Erklärung |
|---|---|
| **Observation** (Micrometer) | Eine Messung mit Anfang und Ende, aus der *gleichzeitig* eine Metrik (ein Timer) und ein Trace-Span entstehen. Diese Plattform benutzt zwei Familien: `einvoice.validation.stage` für die Pipeline-Stufen und `einvoice.pipeline` für die Schritte, die `app` selbst orchestriert. **Ein Name plus ein Tag**, nicht zehn Namen — sonst ist „wie lange dauert die Pipeline?" auf der Metrik-Seite gar nicht formulierbar. |
| **Span / Trace** | Ein *Span* ist eine gemessene Operation, ein *Trace* der Baum aus Spans, der zu einer Anfrage gehört. Der Trace einer Rechnungserstellung liest sich hier als HTTP-Span mit `read-canonical-json`, beiden Mappings, dem XML-Schreiben, den fünf Validierungsstufen und dem transaktionalen Schreiben darunter. |
| **OTLP** (OpenTelemetry Protocol) | Das Transportformat, mit dem Traces und Metriken an ein Backend **geschickt** werden (Push). Die Gegenrichtung wäre *Scraping*, bei dem Prometheus einen Endpunkt der Anwendung abholt. Diese Plattform pusht beide Signale: ein Mechanismus statt zweier, und keine neue Oberfläche, die ein Credential bräuchte (ADR-0012). |
| **Kardinalität** (eines Tags) | Wie viele verschiedene Werte ein Metrik-Tag annehmen kann — und damit, wie viele Zeitreihen daraus entstehen. Ein Tag, dessen Werte aus einem Dokument, einer Anfrage oder der Antwort eines Dritten stammen, ist **unbegrenzt**. Deshalb kommen die Tag-Werte hier ausschließlich aus Konstanten und einem Enum. |
| **Perzentil-Histogramm** | Die Bucket-Grenzen, ohne die ein p95 nicht *ungenau*, sondern **unberechenbar** ist: ein Micrometer-Timer veröffentlicht standardmäßig nur Anzahl, Summe und Maximum, Prometheus sieht dann einen einzigen `+Inf`-Bucket, und `histogram_quantile` antwortet `NaN`. |
| **Advisory Lock** (PostgreSQL) | Eine Sperre, die die Datenbank verwaltet, ohne dass eine Zeile oder Tabelle gesperrt wird — hier `pg_try_advisory_xact_lock`, damit von mehreren Instanzen genau eine den nächtlichen Aufbewahrungs-Job ausführt. Die transaktionsgebundene Variante endet mit der Transaktion, also auch dann, wenn die Instanz mitten im Lauf stirbt. |
| **Forwarded Headers** (`X-Forwarded-For`) | Die Kopfzeilen, mit denen ein Reverse-Proxy der Anwendung mitteilt, wer der *eigentliche* Client war. Sie zu glauben ist hinter einem vertrauenswürdigen Proxy nötig (sonst teilen sich alle anonymen Aufrufer dessen Adresse) und ohne Proxy gefährlich (dann behauptet jeder Aufrufer, wer er will). Deshalb ein Schalter und kein Default: `SERVER_FORWARD_HEADERS_STRATEGY`. |
| **RP-initiated Logout** | Das Abmelden, bei dem die Anwendung („Relying Party") den Browser zusätzlich zum `end_session_endpoint` des Identity Providers schickt, damit auch dessen SSO-Sitzung endet. Diese Plattform meldet **nur lokal** ab — eine benannte, keine versteckte Grenze (SECURITY.md, CHANGELOG). |
| **STRIDE** | Ein Raster zum Sortieren von Bedrohungen: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege. `SECURITY.md` führt es „light", also je Kategorie eine Tabelle mit Maßnahme **und** der Klasse oder dem Test, der sie durchsetzt. |
